# Phase 1: PointMaze Offline PI Rehearsal Plan

Parent plan: [`current-development-plan.md`](./current-development-plan.md).

## Goal

Make the current MuJoCo ball model (`PointMaze`) usable as a complete offline path-integration workflow for the existing `pi_ppo_lstm` stack.

The phase should support:

- standalone `offline_pi_rehearsal` on fixed datasets;
- `offline_pi_probe` on held-out datasets without parameter updates;
- RL warm starts from weights with rehearsed localization / PI features;
- explicit interleaving such as `RL -> offline_pi_rehearsal -> RL -> offline_pi_rehearsal`.

## Scope

- Environment: `PointMaze` only.
- Agent body: current MuJoCo ball model only.
- Data source: datasets generated by `scripts/generate_pointmaze_dataset.py` and `components/dataset_gen/`.
- Model: existing `PathIntegrationRecurrentPPO` and `PathIntegrationRecurrentActorCriticPolicy`.
- Architecture: keep the current shared actor-LSTM PI head design.
- Online rollout PI: preserve `PathIntegrationRecurrentPPO.train()` behavior and do not rename or reimplement it.
- Out of scope: AntMaze support, separate PI/RL recurrent modules, broad zoo experiment-manager rewrites.

## Terminology

- `offline_pi_rehearsal`: PI-only optimizer updates on the current RL model using an offline dataset.
- `offline_pi_probe`: held-out PI evaluation that never updates model parameters.
- `pi_rehearsal_dataset`: offline dataset root used by `offline_pi_rehearsal`.
- `pi_probe_dataset`: held-out offline dataset root used by `offline_pi_probe`.

These names are separate from RL `train` and online RL `eval` terminology.

## Fixed Decisions

- `obs/*` arrays are action-before policy observations used to choose the corresponding `step/action` row.
- `obs/*` arrays align one-to-one with `step/action`, `step/reward`, and the episode offsets.
- `achieved_goal` stays in the offline observation dict because it is the PI target.
- `achieved_goal` must still be dropped from policy features through `CustomCombinedExtractor(drop_keys=['achieved_goal'])`.
- `offline_pi_rehearsal` uses the same model and policy objects as RL.
- `offline_pi_rehearsal` owns a separate optimizer and does not reuse PPO optimizer state.
- Phase 1 includes fixing the PPO optimizer parameter membership so online PI loss can update `path_integration_head`.

## Default Preset Ownership

Keep the Phase 1 PointMaze PI defaults in one implementation-level preset or helper, not duplicated across README, shell scripts, zoo YAML, and planning docs.

The preset should cover the shared env kwargs needed for observation-space parity between dataset generation and the target `pi_ppo_lstm` RL run. `rl-baselines3-zoo/conf/maze_pi.yml` remains responsible for model and feature-extractor settings, including `features_extractor_kwargs=dict(drop_keys=['achieved_goal'])`.

Docs should name the preset and describe the contract. Shell scripts remain experiment notes, not the source of truth for default environment settings.

## Dataset Contract

### Dataset Roots

Use two independent dataset roots:

- `pointmaze_mujoco_pi_rehearsal`
- `pointmaze_mujoco_pi_probe`

Use different seeds by convention:

- `pi_rehearsal_dataset`: `dataset_seed = S`
- `pi_probe_dataset`: `dataset_seed = S + 1`

For grid-cells-torch-scale Phase 1 runs, use 10k rehearsal episodes and 4k probe episodes with `episodes_per_shard=1000` and compact NPZ storage.

Do not add a combined split manifest unless a later workflow needs it.

### Metadata

Add dataset schema fields to `dataset_metadata.json` and shard `dataset_meta_json`:

- `dataset_schema`: `pointmaze_mujoco_zarr`
- `dataset_schema_version`: `1`

This schema version includes the selected policy-compatible `obs/*` arrays listed below.

Dataset metadata should record the data-collection policy as `GridCellRandomWalkForceDriver` and persist its motion and force-control parameters in `policy_params`.

### Collection Policy

Phase 1 PointMaze datasets use a grid-cells-style smooth velocity random walk tracked through the environment's global `x/y` motor action space. The driver samples a correlated heading process and positive speed like the synthetic random-walk reference workflow, converts them to a desired velocity, and uses current `qvel` feedback to emit clipped two-dimensional force actions. It does not use hard-coded arena boundaries, lookahead reflection, or a synthetic collision flag. Wall-contact recovery comes from the four touch-sensor channels exposed by the sensor-aware PointMaze observation. On touch, the driver estimates an observable away-from-wall direction from the four sensor values, chooses the tangent sign from current `qvel` or the previous desired velocity, and combines tangent-biased motion with a weaker away-from-wall component plus bounded jitter. It does not randomly resample heading inside the touch branch. The Phase 1 preset keeps `sensor_aware=True`, so `obs/observation` contains velocity plus those four touch-sensor channels.

Do not use egocentric command semantics for PointMaze dataset generation. The PointMaze MuJoCo model exposes two global slide-joint motor actions.

The touch-sensor recovery direction is an observable approximation from the four sensor sites, not an exact MuJoCo contact normal. Exact continuous contact normals require reading MuJoCo contact data directly and are not part of the Phase 1 dataset driver.

- `obs/observation`
- `obs/start_pos`
- `obs/achieved_goal`
- `obs/desired_goal`

The `obs/*` array shapes follow the current PointMaze observation space for each key. Store these arrays as `float32`, matching the collector's normalized episode arrays. For the Phase 1 preset, `obs/observation` is six-dimensional: two MuJoCo velocity coordinates followed by four touch-sensor channels.

Do not persist raw unbounded `info` payloads in Phase 1.

### Observation Timing

For each timestep `t`, `obs/*[t]` is the policy observation used to choose `step/action[t]`.

For each episode:

- the first `obs/*` row is the reset observation;
- each later `obs/*` row is the observation returned by the previous environment step;
- the final post-step observation after the last action is not required for Phase 1.

The first policy action receives `agent_xy` and `agent_qvel` from the same `env.reset(...)` output; later actions receive them from the previous `env.step(...)` info. The collection policy does not set the initial position.

This keeps offline PI sequence inputs aligned with online SB3 rollout observations.

## Offline Batch Contract

Implement a modular batch source that reads PointMaze dataset shards and yields padded recurrent batches. Compact NPZ shards are the default storage format; directory-style Zarr shards remain readable for existing datasets.

Target module:

- `components/offline_pi_rehearsal.py`

Target functions:

- `load_offline_pi_batches(...)`
- `compute_offline_pi_loss(...)`
- `make_offline_pi_optimizer(...)`
- `run_offline_pi_rehearsal(...)`
- `run_offline_pi_probe(...)`

Batch fields:

- `obs`: dict with `observation`, `start_pos`, `achieved_goal`, and `desired_goal`
- `target_pos`: `(n_seq * max_len, 2)`, usually from `obs/achieved_goal`
- `episode_starts`: `(n_seq * max_len,)`, float or bool
- `mask`: `(n_seq * max_len,)`, bool, where padding is `False`
- `lstm_states_pi`: `(h0, c0)`, each shaped `(n_lstm_layers, n_seq, lstm_hidden_size)`

Observation tensors should be flattened padded recurrent batches:

- `obs[key]`: `(n_seq * max_len, *obs_shape)`
- `episode_starts`: `(n_seq * max_len,)`
- `mask`: `(n_seq * max_len,)`

First implementation strategy:

- support full-episode batches or fixed windows;
- initialize each sequence with zero LSTM state;
- set the first real step of each sequence as `episode_starts = 1`;
- use `mask` only for loss masking, not for skipping LSTM forward;
- do not implement mid-episode burn-in in the first pass.

## PI-Only Forward And Loss

Add a small PI-only policy helper instead of calling the PPO action/value path.

Target policy helper:

- `PathIntegrationRecurrentActorCriticPolicy.forward_pi(...)`

The helper should run only:

- feature extraction for the actor path;
- `lstm_actor` sequence processing;
- `path_integration_head`.

`compute_offline_pi_loss(...)` should use:

- `policy.forward_pi(...)`
- `policy.path_integration_target_encoder(target_pos)`
- `soft_place_cell_cross_entropy(pc_logits, pc_targets, mask=mask)`

It should not compute actions, log probabilities, entropy, value loss, advantages, PPO ratios, or KL early stopping.

## Optimizer Contract

### Online PPO Optimizer Fix

Ensure `path_integration_head` is included in the PPO optimizer used by online `PathIntegrationRecurrentPPO.train()`.

The fix should preserve the current online PI loss location and training semantics. It should only correct optimizer parameter membership.

Add a preflight or test that fails when any trainable `path_integration_head` parameter is missing from `policy.optimizer`.

### Offline Optimizer

`make_offline_pi_optimizer(...)` must create a separate optimizer instance.

Include only PI-path parameters:

- actor feature extractor parameters used by the PI/action path;
- `lstm_actor` parameters;
- `path_integration_head` parameters.

Exclude PPO-only or value-path parameters:

- `action_net`
- `log_std`
- `value_net`
- `lstm_critic`
- critic-only feature extractor parameters
- `mlp_extractor` unless a later explicit decision requires it

The offline optimizer must not share object identity or optimizer state with `policy.optimizer`.

## Rehearsal And Probe Semantics

### `offline_pi_rehearsal`

- Set the policy to training mode.
- Iterate over `pi_rehearsal_dataset` batches.
- Compute PI-only loss.
- Backpropagate only through the offline optimizer parameter set.
- Log metrics under `offline_pi/*`.
- Do not update PPO optimizer state.

### `offline_pi_probe`

- Set the policy to evaluation mode or use no-grad evaluation.
- Iterate over `pi_probe_dataset` batches.
- Report PI loss and localization metrics.
- Do not call `backward()`.
- Do not call any optimizer step.
- Leave the model `state_dict` unchanged.

## RL Integration Surface

First add standalone APIs and an optional standalone script. Avoid depending on `rl-baselines3-zoo` experiment-manager internals.

Later integration can be a lightweight SB3 callback or runner hook with explicit settings:

- `offline_pi_rehearsal_interval`

## Test Plan

### Dataset Tests

- `obs/*` arrays exist in shards.
- `obs/*` first dimension equals `sum(episode_lengths)`.
- `episode_offsets` correctly slice `obs/*` per episode.
- The first observation row per episode is the reset observation.
- For each non-initial row, `obs/*[t]` equals the observation returned by the previous step.
- Test fixtures prove `step/action[t]` was chosen from `obs/*[t]`.
- Obs key drift fails fast.
- Missing `observation`, `start_pos`, `achieved_goal`, or `desired_goal` fails fast.
- Dataset metadata records observation-space parity fields: `achieved_goal_aware`, `start_pos_aware`, and `target_aware`.
- `obs/achieved_goal` is a 2D PI target when `achieved_goal_aware=True`.
- `obs/start_pos` and `obs/desired_goal` shapes match the target RL observation space instead of being hard-coded to 2D.
- Dataset metadata contains `dataset_schema` and `dataset_schema_version`.
- `episode_summaries_json` includes all required summary fields.
- Dataset metadata records `GridCellRandomWalkForceDriver` and its motion/force-control parameters.
- Dataset distribution analysis reports occupancy coverage, action statistics, and trajectory previews.

### Batch Source Tests

- Loader returns the four policy observation keys.
- `target_pos` comes from `achieved_goal` and has shape `(n_seq * max_len, 2)`.
- `episode_starts`, `mask`, and `lstm_states_pi` match the recurrent batch contract.
- Padding entries have `mask = False`.

### PI Policy And Optimizer Tests

- `forward_pi(...)` runs without actions or value outputs.
- Changing only `achieved_goal` does not change PI logits when the feature extractor drops `achieved_goal`.
- Online PPO optimizer includes `path_integration_head` parameters.
- Offline optimizer is not `policy.optimizer`.
- Offline optimizer includes the actor feature extractor, `lstm_actor`, and `path_integration_head`.
- Offline optimizer excludes action and value heads.
- Optimizer tests should verify parameter identity and parameter names so shared feature extractor cases are explicit.

### Rehearsal And Probe Tests

- `compute_offline_pi_loss(...)` runs on a padded recurrent batch.
- `offline_pi_probe` leaves every `state_dict` tensor unchanged.
- `offline_pi_rehearsal` changes at least one PI-path parameter.
- `offline_pi_rehearsal` leaves action/value head parameters unchanged.
- PPO optimizer `state_dict()` remains unchanged after offline rehearsal.
- A minimal shard-to-PI smoke test runs `load_offline_pi_batches(...) -> forward_pi(...) -> compute_offline_pi_loss(...) -> offline_pi_rehearsal/probe`.

## Success Criteria

- `pi_rehearsal_dataset` and `pi_probe_dataset` can be generated reproducibly for PointMaze.
- Offline batches feed the same `PathIntegrationRecurrentPPO` model used by RL.
- Online PPO updates can train `path_integration_head` through the existing online PI loss.
- `offline_pi_rehearsal` performs PI-only updates with a separate optimizer.
- `offline_pi_probe` reports PI metrics without changing parameters.
- Existing online rollout PI behavior remains unchanged apart from the optimizer membership fix.
- Phase 1 remains limited to the PointMaze MuJoCo ball model.
